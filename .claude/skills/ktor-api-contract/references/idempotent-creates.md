# Idempotent creates and concurrency on the wire

## The client names what it creates

Every creation body carries the new resource's id (UUIDv7, generated by the client), in a field
called **`id`** — on a report, a message and an adjustment too, never `reportId`/`messageId`. The
command carries it into the domain, so a create needs no separate idempotency infrastructure
([`kotlin-domain-modeling`](../../kotlin-domain-modeling/SKILL.md)).

| Request                                   | Answer                                                    |
|-------------------------------------------|-----------------------------------------------------------|
| new `id`                                  | `201` + the resource                                      |
| same `id`, same content (a retry)         | **the same** resource and status; nothing written, nothing held again (a balance, quota, stock) |
| same `id`, different content              | `409 ALREADY_EXISTS` (`details.field = "id"`)            |
| same `id`, and the first answer carried a **one-time secret** (an invitation code, a dependant's sign-in code) | `409 ALREADY_EXISTS` **without writing** — the secret exists once and is never shown again |

The only creates without a client id are the ones **before a tenant exists** (register an account,
create a tenant): the client names no ids before it has a tenant. They are a closed list,
`KNOWN_SERVER_ID_CREATES` in `ContractConventionsTest`, next to "no request body names the id of
what it creates otherwise".

Mine it prevents: a retry after a lost response that creates a second resource or holds a second
amount — and the batch client that reads its own replay as an error (see `kotlin-testing-strategy`,
"partial failure of a batch").

## Ledger keys: from the event, or from the human

An append-only ledger keyed by `(wallet_id, source_key)` derives the key from **what happened**
(`accepted:<itemId>`, `reversal:<entryId>`). A manual adjustment has no "what happened" — it is a
person's decision, and a person may legitimately decide the same thing twice. So its key is
`adjustment:<id>` with the `id` sent by the client: two decisions are two ids, a retry of one is
the same id. A key from the content (`adjustment:<member>:<amount>:<ts>`) is an illusion of safety:
two identical decisions in one millisecond are not a replay.

## `version` in the body, not `ETag`/`If-Match`

Optimistic concurrency travels as `version` inside the request DTO. An offline client queues
commands and drains them later; the version must be part of the **command**, not of an HTTP header
taken from a response long gone. One mechanism serves online and offline. A stale version is
`409 CONFLICT` — a different code from `ALREADY_EXISTS`, so a queue can tell "re-read and replay"
from "already there".

## Seams, deliberately not built

- **`Idempotency-Key` header** for non-creating commands with side effects needs a server-side store
  that replays responses. Build it when one command needs it (the usual threshold: money moves);
  until then client ids + `version` cover every route.
- **Conditional GET / HTTP caching** — freshness comes from the live channel (SSE), not from `ETag`.

## Async is a status, not a queue

A command whose effect is computed later answers immediately with the resource in its current
state (`201`, `review.state = Pending`); the result arrives as a delta on the live channel (or a
push). No `202 Accepted` job resources, no polling endpoints — one pattern for every background
effect. `202` is reserved for "accepted, will happen at a date", with that state in the body
(`{deletingAt}`).

Evidence: family-planner ADR 0050 (the command carries the new id), ADR 0014 (offline queue →
`version` in the body), step 76 A3 (`id` in every create body, `KNOWN_SERVER_ID_CREATES`),
`api-design.md` «Идемпотентность мутаций» (adjustment key, `Idempotency-Key` seam), step 80
(`202 {deletingAt}`).
