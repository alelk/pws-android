# Мониторинг: crash-репортинг, non-fatal ошибки и продуктовая аналитика

> **Статус:** РЕАЛИЗОВАН (код) — 2026-08-07. Осталось только то, что делается руками в консолях:
> T-E01 (алерты AppMetrica), T-E02 (Android Vitals / RuStore vitals), T-F05 (Play Data Safety /
> RuStore декларации), T-H02/T-H03 (проверка на реальном устройстве). Чек-лист —
> [`docs/release-workflow.md`](../../release-workflow.md), архитектура —
> [`docs/monitoring.md`](../../monitoring.md).
>
> **Отступления от плана (осознанные):**
> 1. **`Telemetry` живёт в `:domain`, а не в `:features`** (T-A01/O4). Non-fatal нужно репортить из
>    `data/content-delivery` — модуля данных, который не должен зависеть от Compose-UI-модуля
>    `:features`. `:domain` уже зависимость обоих. Дефолтный биндинг `NoOpTelemetry` по-прежнему в
>    `featuresModule` (T-A02 без изменений).
> 2. **AppMetrica Gradle Plugin не подключён** (T-B06). Актуальная версия 1.0.1 построена на
>    удалённом `com.android.build.gradle.api.ApplicationVariant` и несовместима с AGP 9.x проекта.
>    Вместо неё — задача `stageAppMetricaMapping<Variant>`, кладущая `mapping.txt` в
>    `output/appmetrica-mapping/mapping-<variant>-<versionName>-<versionCode>.txt` (+ выгрузка
>    артефактом в CI); загрузка в консоль — ручной шаг в релизном чек-листе.
> 3. **Согласие хранится в SharedPreferences, а не в DataStore** (T-F03). Значение нужно
>    **синхронно** в `Application.onCreate()` до активации SDK; DataStore даёт только suspend-чтение.
> 4. **Firebase (Phase G) не делался** — явно опционален и вне базового объёма.
>

## 1. Цель

Как можно **раньше выявлять баги** на устройствах пользователей и получать их **репорты
разработчику** (падения, ANR, пойманные исключения), плюс собирать **базовую продуктовую
статистику** (какие экраны/фичи используются). Решение должно:

1. **Надёжно работать у российских пользователей и в `rustore`-сборке** (критично — большая доля
   аудитории). Никакой зависимости от Google-доступности как единственного канала.
2. Быть **максимально бесплатным и простым** (без своей инфраструктуры/сервера).
3. Ложиться на текущий стек (KMP `pws-core` + Compose Multiplatform + Koin + per-flavor
   `FlavorIntegration`), инструментировать в т.ч. shared-код, а не только Android-обёртку.
4. **Уведомлять разработчика** о новых/участившихся ошибках (email/push-алерты).

## 3. Факты разведки (проверено в коде)

### 3.1. Флейворы и точка подключения per-flavor

- Dimension `contentLevel`, флейворы: **`ru`, `full`, `uk`** (Google Play) + **`rustore`** (RuStore)
  — `app-compose/build.gradle.kts:161–185`.
- Готовый паттерн per-flavor интеграции:
  `app-compose/src/<flavor>/kotlin/.../flavor/FlavorIntegration.kt`
  экспортирует `flavorKoinModules(): List<Module>`, `MONETIZATION`, `flavorShowPaywall()`. Уже
  используется для RuStore Pay SDK (`rustore/.../FlavorIntegration.kt`) — **идеальная точка** для
  подключения провайдера телеметрии, если он различается по флейворам.

### 3.2. Единая точка старта приложения

- `app-compose/src/main/kotlin/.../PwsComposeApplication.kt` — `onCreate()`:
    - `startKoin { ... }` собирает модули; **flavor-модули грузятся последними и «выигрывают»**
      (`*flavorKoinModules().toTypedArray()`).
    - есть `applicationScope` с `CoroutineExceptionHandler`, который сейчас **только** пишет
      `android.util.Log.e("PwsApp", "Background task failed", e)` — готовая точка, чтобы
      дополнительно
      отправлять non-fatal в телеметрию.
    - `appInfoModule` уже достаёт `versionName` и биндит `PwsAppInfo(version)` — версию можно
      прокинуть
      как атрибут/тег в телеметрию (для группировки по релизам).
- `BuildConfig.BUNDLE_VARIANT` (`release`/`debug`) и `BuildConfig.CATALOG_URLS` уже прокидываются —
  тем же способом заведём `BuildConfig.APPMETRICA_API_KEY` (без хардкода секрета — из gradle
  property / переменной окружения).

### 3.3. Куда встраивать инструментирование

- `pws-core` — KMP (jvm/js/android). Интерфейс `Telemetry` в `features`-модуле `commonMain` даёт
  доступ из use-cases/скринмоделей; на не-Android таргетах — no-op реализация.
- `data/content-delivery/.../di/ContentDeliveryModule.kt` — импорт/скачивание сборников; типичное
  место для non-fatal (сбой скачивания/декода/импорта) и событий воронки установки.
- Voyager-навигация (см. `voyager-navigation` skill) — единая точка для авто-логирования показов
  экранов (screen-view события).

### 3.4. Приватность (важно для деклараций магазинов)

- Приложение содержит **пользовательские правки песен** и личный контент. В breadcrumbs/атрибуты
  **нельзя** класть тексты песен/PII. Требуется явная политика скраббинга и декларации Data Safety
  (Play) / согласие по 152-ФЗ (РФ).

## 4. Архитектура решения (сквозной поток)

```text
СЛОЙ АБСТРАКЦИИ (pws-core: features/commonMain)
  interface Telemetry {
    fun recordError(t: Throwable, attrs: Map<String,String> = emptyMap())  // non-fatal
    fun log(message: String)                                               // breadcrumb
    fun event(name: String, params: Map<String,Any?> = emptyMap())         // product analytics
    fun setUserProperty(key: String, value: String?)
  }
  object NoOpTelemetry : Telemetry { /* default для js/jvm/тестов */ }

ANDROID-РЕАЛИЗАЦИЯ (app-compose)
  AppMetricaTelemetry(context) — обёртка над AppMetrica:
    recordError → AppMetrica.reportError / reportUnhandledException-помощники
    event       → AppMetrica.reportEvent(name, params)
    log         → крошки/AppMetrica.reportEvent("log", ...)  (без PII)
  ↑ инициализация SDK в PwsComposeApplication.onCreate() ПЕРВЫМ делом
    (до тяжёлого init), чтобы ловить ранние падения. Ставит глобальный
    crash+ANR handler автоматически (AppMetrica делает это сама).

DI
  appTelemetryModule { single<Telemetry> { AppMetricaTelemetry(androidContext()) } }
  (один провайдер на все флейворы; при желании — переопределение через flavorKoinModules)

КАНАЛЫ РЕПОРТИНГА РАЗРАБОТЧИКУ
  AppMetrica Console: crashes/ANR/non-fatal + email/push-алерты на новые/участившиеся ошибки
  Android Vitals (Play Console)   — бесплатно, gplay-флейворы, zero-code
  RuStore Console vitals          — бесплатно, rustore, zero-code

ДЕОБФУСКАЦИЯ
  AppMetrica Gradle plugin — авто-загрузка ProGuard/R8 mapping.txt по релизам,
  иначе стектрейсы обфусцированы.
```

Ключевой принцип: **бизнес-код зависит только от `Telemetry`** (из `pws-core`), не от AppMetrica.
Провайдер живёт в `app-compose` и подменяем — если завтра добавим Firebase/Sentry, бизнес-код не
меняется.

## 5. Фазы и задачи

### Phase A — Абстракция телеметрии (без внешних SDK)

- **T-A01** — Интерфейс `Telemetry` в `pws-core` `features/commonMain`
  (`io.github.alelk.pws.features.telemetry.Telemetry`) с методами `recordError`, `log`, `event`,
  `setUserProperty`. Плюс `object NoOpTelemetry`.
- **T-A02** — Дефолтный биндинг `NoOpTelemetry` в `featuresModule` (чтобы код, вызывающий
  `Telemetry`, работал в тестах и на не-Android таргетах без реального провайдера).
- **T-A03** — Прокинуть `Telemetry` в 1–2 ключевых места как smoke (напр.
  `CoroutineExceptionHandler`
  в `PwsComposeApplication` и один импорт-сбой в content-delivery), чтобы проверить сквозной вызов
  ещё до подключения SDK (пойдёт в no-op).

### Phase B — Подключение AppMetrica (crash + ANR автоматически)

- **T-B01** — Зависимость AppMetrica: артефакт в `libs.versions.toml`, добавить в `app-compose`
  (все флейворы). AppMetrica доступна и без Google Play Services.
- **T-B02** — `BuildConfig.APPMETRICA_API_KEY`: значение из gradle property/env (не коммитить ключ;
  положить в `local.properties`/CI-secret, дефолт-заглушку для локали).
- **T-B03** — `AppMetricaTelemetry(context)` в `app-compose` реализует `Telemetry` поверх
  AppMetrica.
- **T-B04** — Инициализация SDK в `PwsComposeApplication.onCreate()` **самым первым** (до тяжёлой
  инициализации/Koin по возможности), сессии/крэши/ANR включаются автоматически. Прокинуть версию из
  `PwsAppInfo`/`versionName` и `BUNDLE_VARIANT` как атрибуты окружения.
- **T-B05** — `appTelemetryModule { single<Telemetry> { AppMetricaTelemetry(androidContext()) } }`,
  добавить в `startKoin` (перед flavor-модулями, чтобы flavor мог переопределить при желании).
- **T-B06** — Деобфускация: AppMetrica Gradle plugin для авто-загрузки `mapping.txt` по релизам
  (release-сборки обфусцированы R8). Проверить, что маппинг привязан к versionName/versionCode.

### Phase C — Non-fatal ошибки и breadcrumbs (главная цель — ранний отлов)

- **T-C01** — `CoroutineExceptionHandler` в `PwsComposeApplication` дополнительно вызывает
  `telemetry.recordError(e, ...)` (сейчас только `Log.e`).
- **T-C02** — Инструментировать критичные Either-ошибки/`catch` в content-delivery (
  скачивание/декод/
  импорт бандлов, seed) — репортить как non-fatal с атрибутами (`bookId`, `stage`), **без** текстов
  песен/PII.
- **T-C03** — Точечно обернуть рискованные места: Room/DB-операции, парсинг каталога, платежи
  (`rustore` PaymentController). Non-fatal вместо тихого проглатывания.
- **T-C04** — Хлебные крошки на ключевых переходах (открыть песню, поиск, установка сборника) — для
  контекста стектрейса. Только идентификаторы/действия, не контент.

### Phase D — Продуктовая аналитика (статистика)

- **T-D01** — Авто-логирование показов экранов через Voyager (единая обёртка навигации) →
  `telemetry.event("screen_view", {screen})`.
- **T-D02** — Небольшой словарь ключевых событий (напр.: `song_open`, `search`, `book_install`,
  `book_import`, `onboarding_complete`, `paywall_shown`/`purchase` для `rustore`,
  `donation_prompt`).
  Завести константы имён событий в одном месте (`pws-core`), чтобы не плодить строки.
- **T-D03** — User-properties/атрибуты для срезов: флейвор, `BUNDLE_VARIANT`, язык устройства
  (`deviceLanguage` уже есть в DI), число установленных сборников. Без PII.

### Phase E — Алерты разработчику + store-vitals

- **T-E01** — В AppMetrica Console настроить **email/push-алерты** на новые/участившиеся крэши и
  падение crash-free доли — это и есть «баги репортятся мне как можно раньше».
- **T-E02** — Включить/проверить **Android Vitals** (Play Console) для gplay-флейворов и **RuStore
  Console** vitals для `rustore` — бесплатный второй источник крэшей/ANR без кода.
- **T-E03** — Договориться о привязке к релизам: versionName/versionCode как измерение везде (
  AppMetrica
    + маппинг), чтобы видеть регрессии по версиям.

### Phase F — Приватность / согласие / декларации

> **Правовой контекст (не юрконсультация, ориентир).** Crash- и analytics-данные AppMetrica содержат
> идентификаторы устройства/инсталляции (device/app-instance id, иногда IP) → это **псевдонимные
> персональные данные**, а не «анонимные». Поэтому раскрытие сбора **обязательно** независимо от
> формулировки «анонимно». Требования: (1) **правила магазинов** — Play Data Safety + Privacy Policy,
> RuStore-аналог; (2) **152-ФЗ (РФ)** — политика обработки ПДн, первичное хранение данных россиян в
> РФ (AppMetrica удовлетворяет); (3) **GDPR (EU)** — для аналитики нужен **opt-in до начала сбора**,
> для чистого crash-репортинга допустим «законный интерес» + раскрытие. Решение по строгости — O3.

- **T-F01 — PII-скраббинг (обязательно).** Аудит: в события/атрибуты/крошки **не** попадают тексты
  песен, пользовательские правки, поисковые запросы с контентом, персональные данные. Только
  идентификаторы действий/экранов, флейвор, версия, язык, счётчики. Единый список разрешённых ключей
  событий (константы в `pws-core`) + ревью на этапе Phase C/D. Хелпер, отбрасывающий значения свыше
  лимита/по чёрному списку ключей.
- **T-F02 — Privacy Policy (обязательно).** Текст политики конфиденциальности: **что** собирается
  (крэши/ANR/non-fatal + продуктовые события), **кем обрабатывается** (Яндекс/AppMetrica как
  обработчик, хранение в РФ), **зачем** (диагностика и улучшение приложения), **как отказаться**
  (тумблер в настройках). Разместить: экран «О приложении»/настройки (ссылка) **и** карточка Play/
  RuStore. Черновик-заготовку положить в `docs/` (напр. `docs/privacy-policy.md`) + хостинг URL.
- **T-F03 — Тумблер согласия в настройках (обязательно).** Пункт «Отправлять отчёты о сбоях и
  анонимную статистику» → под капотом `AppMetrica.setDataSendingEnabled(enabled)`. Состояние хранить
  (DataStore `pws-app-preferences`, где уже лежат настройки). Применять **до** отправки первых
  событий на старте (читать флаг до/сразу после init SDK).
- **T-F04 — Первичное согласие по режиму (см. O3).** Реализовать выбранный режим: (вариант по
  умолчанию) crash-репортинг включён + аналитика с opt-out; **либо** (строгий EU-режим) экран
  согласия на онбординге (у нас уже есть онбординг первого запуска — добавить шаг/чекбокс), сбор
  аналитики **выключен** до явного согласия. Флейвор/рынок может влиять на дефолт.
- **T-F05 — Декларации магазинов (обязательно перед релизом).** Заполнить **Play Data Safety**
  (Crash logs = Yes, Analytics = Yes, указать назначение, «данные не продаются», шифрование в
  транзите) и **RuStore**-аналог. Синхронизировать формулировки с Privacy Policy (не должны
  расходиться — иначе отклонение при ревью).
- **T-F06 — Чек-лист соответствия.** Короткий чек-лист в `docs/release-workflow.md`: перед публичным
  релизом с включённым сбором — Privacy Policy опубликована и слинкована, Data Safety/RuStore
  заполнены, тумблер работает, PII-аудит пройден.

### Phase G — (опционально) Firebase для gplay-native

- **T-G01** — Только если позже понадобится: `Telemetry`-провайдер на базе Firebase Crashlytics +
  Analytics, подключаемый **через `flavorKoinModules()`** в `ru/full/uk` (не в `rustore`).
  Бизнес-код
  не меняется. Явно вне базового объёма (пользователь выбрал «просто/бесплатно»).

### Phase H — Тесты / проверка

- **T-H01** — Unit: `NoOpTelemetry` не падает; вызовы `Telemetry` из use-cases покрыты (
  мок-провайдер
  фиксирует события/ошибки).
- **T-H02** — Ручная проверка: тестовое `recordError`/`event` из debug-сборки долетает в AppMetrica
  Console (debug-ключ или отдельное debug-приложение в консоли).
- **T-H03** — Проверить деобфускацию: искусственный краш в release-сборке приходит с читаемым
  стектрейсом (маппинг загрузился).
- **T-H04** — Регресс: чистые флейворы собираются, `rustore` работает, инициализация телеметрии не
  ломает старт и онбординг первого запуска.

## 6. Открытые под-решения (уточнить при реализации)

- **O1 — Один AppMetrica-app или несколько.** Один API-ключ на приложение (срез по флейвору/варианту
  через атрибуты) vs отдельные приложения в консоли под `rustore`/gplay. *Рекомендация:* один ключ +
  атрибут `flavor` — проще; разнести позже, если срезы неудобны.
- **O2 — debug vs release события.** Чтобы не засорять статистику dev-запусками: отдельный
  debug-ключ
  или `setDataSendingEnabled(false)` в debug. *Рекомендация:* не слать из debug по умолчанию,
  включать
  тумблером для проверки.
- **O3 — Строгость согласия (закрыто рекомендацией, финализировать при реализации).** Сбор данных
  требует раскрытия в любом случае (см. Phase F). Открыт только **режим согласия**:
  - **Режим по умолчанию (рекомендуемый):** **crash-репортинг включён** по умолчанию (законный
    интерес, низкий риск) + **продуктовая аналитика с opt-out** (тумблер в настройках, T-F03). Плюс
    Privacy Policy и декларации. Простой UX, приемлемый риск для РФ-центричной аудитории.
  - **Строгий EU-режим:** если EU-аудитория станет значимой — **opt-in на онбординге**, аналитика
    (и, по-хорошему, non-essential сбор) **выключены** до явного согласия (T-F04). Можно включать
    per-flavor/по локали.
  *Рекомендация:* стартовать с режима по умолчанию; заложить архитектуру тумблера
  (`setDataSendingEnabled`) так, чтобы переключение на строгий режим было конфигом, а не переписью.
  Обязательно перепроверить актуальные требования Play/RuStore/152-ФЗ/GDPR перед публичным релизом.
- **O4 — Место интерфейса `Telemetry`.** `features` vs `domain` модуль `pws-core`. *Рекомендация:*
  `features` (ближе к скринмоделям/use-cases, которые эмитят события); domain-слой репортит через
  тот
  же интерфейс.

## 7. Риски и крайние случаи

- **R1 — Секрет в репозитории.** API-ключ нельзя коммитить. Митигация: T-B02 (gradle property/CI
  secret), проверить `.gitignore`.
- **R2 — Обфусцированные стектрейсы** в release без загрузки маппинга → отчёты нечитаемы. Митигация:
  T-B06 (AppMetrica Gradle plugin).
- **R3 — Утечка PII** в события/крошки (тексты песен, правки). Митигация: Phase F, ревью ключей.
- **R4 — Инициализация SDK ломает/замедляет старт** или конфликтует с онбордингом первого запуска.
  Митигация: init лёгкий и первый; T-H04 регресс.
- **R5 — Двойной учёт крэшей** (AppMetrica + store-vitals) — это ок, разные источники; не считать
  как
  «в 2 раза больше».
- **R6 — Доступность AppMetrica-эндпоинта.** Yandex-инфраструктура доступна в РФ и глобально, но
  проверить, что события уходят с реальных устройств (T-H02).
- **R7 — Несоответствие правилам магазина/закону.** Сбор без Privacy Policy / без декларации Data
  Safety / без раскрытия → **снятие с публикации** (Play/RuStore), риск по 152-ФЗ/GDPR. «Анонимно» не
  освобождает: crash/analytics содержат device-id → псевдонимные ПДн. Митигация: Phase F обязательна
  **до** публичного релиза с включённым сбором (T-F06 чек-лист); формулировки Policy ↔ Data Safety
  синхронны.

## 9. Порядок реализации (рекомендуемый)

1. **Phase A** (абстракция `Telemetry` + no-op) — изолированно, ничего не ломает, сразу можно
   вызывать
   из кода.
2. **Phase B** (AppMetrica init + crash/ANR) — базовый уровень «ловим падения» готов.
3. **Phase C** (non-fatal + breadcrumbs) — главная цель: ранний отлов не-фатальных багов.
4. **Phase E** (алерты + store-vitals) — чтобы репорты реально доходили до разработчика.
5. **Phase D** (аналитика) — статистика.
6. **Phase F** (приватность/декларации) — до публичного релиза с включённым сбором.
7. **Phase G** (Firebase) — опционально, позже.

Такой порядок даёт рабочую вертикаль «падение на устройстве → отчёт в консоли + алерт мне» уже после
Phase B–E, до продуктовой аналитики и опциональных провайдеров.
