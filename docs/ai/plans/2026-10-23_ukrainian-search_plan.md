# Поиск по песням: корректная поддержка украинского (и нормализация кириллицы)

> **Статус:** ПЛАН v2 — 2026-10-23. Доработан после сверки с кодом обоих репозиториев и
> экспериментов на SQLite 3.46.1 (см. §8). Ждёт решений из §5.
> **Ветка:** от `next`, `fix/uk-search` (в обоих репозиториях: `pws-core`, `pws-android`)
> **Повод:** отзыв украинского пользователя: «поиск ничего не находит».
> **Реальной украинской БД в репозиториях нет** — проверка на ней остаётся задачей T-0.2.

## 0. TL;DR

Интерфейс на украинском в порядке (303/304 ключа, см. §7). Сломан **поиск**, три независимые
причины:

| #  | Проблема                                                                                                                                                                                                                                                                                                                   | Серьёзность                                                           | Нужна миграция БД         |
|----|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------|---------------------------|
| P1 | Ввод пользователя уходит в `MATCH` без экранирования: `(бог`, `а"б`, `бог AND`, `NOT` → `malformed MATCH expression`. `SearchScreenModel` ловит исключение и показывает экран ошибки (не краш); системный `SearchManager` (`PwsDataProvider`) — не ловит и к тому же склеивает слова звёздочкой (`свят бог` → `свят*бог*`) | Высокая                                                               | Нет                       |
| P2 | Индекс не сворачивает украинские буквы: «ганок» ≠ «Ґанок», «едини» ≠ «Єдиний», «ижак» ≠ «їжак», «пять» ≠ «п'ять»                                                                                                                                                                                                           | Высокая (вероятная основная жалоба)                                   | **Да** (15 → 16)          |
| P3 | Книга с `book_statistic.priority = 0` исключена из поиска целиком. По коду `priority > 0` = «книга включена пользователем»; при этом `portable.Book.priority` по умолчанию `0`, и `BookContentWriterImpl` при каждой установке/обновлении перезаписывает приоритет значением из бандла                                     | Высокая, если бандлы каталога идут без `priority` — проверить (T-0.2) | Нет (починка данных — да) |

Порядок: **Фаза 1 (P1 + строка uk) выпускается отдельно и быстро** → Фаза 3 (P3, если T-0.2
подтвердит) → Фаза 2 (P2). Фазы 2 и 3 независимы; Фаза 3 дешевле и может оказаться реальной причиной
жалобы — поэтому до Фазы 2.

## 1. Что установлено (факты)

### 1.1. Схема и запросы

- `songs_fts` — `FTS4`, `tokenize=unicode61`, `content=songs` (внешний контент), объявлена
  Room-сущностью
  `SongFtsEntity` с `@Fts4(contentEntity = SongEntity::class)`
  (`pws-core/data/db-room/src/commonMain/.../song/SongFtsEntity.kt`). Схема v15, `15.json`
  экспортируется в `pws-core/data/db-room/schemas/`. `MIGRATION_14_15` — в
  `pws-android/data/db-android/.../migrations.kt`, в Android-форме (`SupportSQLiteDatabase`),
  регистрируется в `PwsDatabaseProvider` и в тестовом
  `pwsDbForTest.kt` (db-android).
- **Room генерирует и владеет триггерами синхронизации** (`PwsDatabase_Impl.kt`, проверено по
  сгенерированному коду):
  `room_fts_content_sync_songs_fts_{BEFORE_UPDATE,BEFORE_DELETE,AFTER_UPDATE,AFTER_INSERT}` с
  **сырым**
  текстом. Они создаются в `createAllTables`, сбрасываются в `onPreMigrate` (`dropFtsSyncTriggers` —
  по префиксу имени `room_fts_content_sync_`) и **пересоздаются в `onPostMigrate` после каждой
  миграции**.
- **Room валидирует FTS-таблицу при открытии**: `FtsTableInfo` сравнивает колонки и опции
  (`tokenize=`, `content=`, …) объявления в БД с ожидаемым. Расхождение → `IllegalStateException`
  «Migration didn't properly handle songs_fts»; `SelfHealingOpenHelper` ловит её, но сбрасывает файл
  только при
  `user_version = 0`, так что на живой БД это краш при старте.
- Запрос строит `buildFtsPrefixQuery` (`pws-core/data/repo-room/.../song/ftsQuery.kt`): режет по
  пробелам, добавляет `*`. Никакой фильтрации синтаксиса FTS. Используется в
  `SongSearchRepositoryImpl` (оба метода).
- Второй вход в тот же индекс — системный `SearchManager`: `PwsDataProvider` (db-android) →
  `androidMain/SongDao.kt` (3 запроса: по имени через `s.name MATCH`, по лирике, по номеру). Он
  формирует запрос сам: `trim().replace("\\s+", "*") + "*"`, то есть многословный ввод превращается
  в один токен `свят*бог*`.
  `db-android` зависит от `db-room`, но **не** от `repo-room`, где лежит `buildFtsPrefixQuery`.
- Ограничение выдачи: `bs.priority > 0` (2 запроса в `SongDaoBase.kt`, 3 в `androidMain/SongDao.kt`,
  `getActiveTagSongsFlow`, `BookStatisticDao.getAllActive`).
- Все пути записи песен идут через DAO (`BookContentWriterImpl`, `RestoreBackupUseCase`,
  `migrateDataFromPrevDatabase` в db-android) — любые триггеры на `songs` их покроют.
  `SongDaoBase.insert`
  использует `OnConflictStrategy.REPLACE` — см. R9.
- `snippet(songs_fts, '<b><font color=#247b34>', …)` отдаётся в UI; `HighlightedText.kt` уже
  нормализует
  `<b><font>` → `<mark>` и понимает `<mark>` напрямую.
- Потребители `db-room`: `repo-room`, `portable-data`, `db-room-test-fixtures` (pws-core);
  `db-android`,
  `content-delivery`, `app-compose` (pws-android). Серверных потребителей нет. Таргеты `db-room`:
  android, jvm, ios (`pws.kmp.android.nojs`); тестовые сборщики БД — 4 `pwsDbForTest` в db-room
  (common/jvm/native/androidHost),
  `inMemoryPwsDb()` в repo-room, по одному в `BackupUseCasesTest` и `BookLibraryUseCasesTest`.
- Тесты поиска (`FtsQueryTest`, `SongSearchRepositoryImplTest`) — русский/английский текст; тестов
  на `songs_fts`
  в `db-room` нет. Побочно (вне скоупа, §7): `ORDER BY matchinfo DESC` сортирует по BLOB,
  `rank = 1f` константа.

### 1.2. Поведение SQLite (эксперимент, 3.46.1; на bundled SQLCipher перепроверить — T-0.1)

- `unicode61` сворачивает регистр кириллицы (`Свят` = `свят`), но **не** сворачивает `ґ/г`, `є/е`,
  `ї/і`, `і/и`,
  `ё/е`, `й/и` (`remove_diacritics` покрывает только латиницу). Ударение U+0301 поиску не мешает.
- Апострофы `'` U+0027, `’` U+2019, `‘` U+2018, `` ` `` U+0060, `´` U+00B4 — разделители токенов
  («п'ять» → «п» + «ять»). **`ʼ` U+02BC (modifier letter apostrophe — «правильный» украинский
  апостроф) — буква**, «пʼять» — один токен `пʼять`; ни «пять», ни «п'ять» его не находят.
  Нормализатор обязан удалять и его.
- Сборка с `SQLITE_ENABLE_FTS3_PARENTHESIS` (enhanced syntax): ошибку дают `(`, `)`, `"` без пары,
  `AND`/`OR`/`NOT`/
  `NEAR` не на месте; `-бог`, `бог:` ошибки не дают. Android-SQLite и SQLCipher собираются с этим
  флагом (подтвердить `PRAGMA compile_options` в T-0.1).
- Экранирование: токен в двойных кавычках со звёздочкой **внутри** — `"госп*"` — работает как
  префикс;
  `"госп"*` — нет. `"AND"`, `"not*"` в кавычках — обычные термы.
- **`FTS4 content=<view>` работает только если у вьюхи есть колонка, названная буквально `rowid`**
  (`SELECT id AS rowid, …`). Без неё (неявный rowid или колонка `docid`) все документы получают
  `docid = 0`, поиск возвращает мусор, `integrity-check` падает «database disk image is malformed».
  С `id AS rowid` корректно работают `rebuild`, вставка/обновление/удаление через триггеры,
  `snippet()`, `integrity-check`.
- `snippet()` по view-контенту возвращает **нормализованный** текст («Ганок Единий…») — см. §3.3.
- `lower()` в SQLite без ICU — только ASCII; для кириллицы в SQL нужны пары обоих регистров
  (тонкость для §3.1).

### 1.3. Приоритет книги (P3) — семантика установлена по коду

- `BookStatisticRepository`: «Statistics of the enabled books (priority > 0)»; `CreateBookCommand.priority =
  if (enabled) 10 else 0`; `SettingsScreenModel` переключает книгу `0 ↔ lastKnown | 1`. **
  `priority = 0` = «выключена пользователем»**, D3 из v1 закрыт.
- `portable.Book.priority: Int = 0` (по умолчанию!), `BookBundle.toBookContent()` копирует как есть,
  `BookContentWriterImpl:86` делает `upsert(BookStatisticEntity(id, priority = book.priority))` при
  **каждой**
  установке и обновлении. Следствия: (a) бандл без явного `priority` ставит книгу выключенной; (b)
  обновление книги затирает выбор пользователя (включил/выключил). Ни один use-case установки
  приоритет после записи не поднимает (grep по `features/booklibrary`,
  `domain/booklibrary/usecase` — пусто).

## 2. Цели и критерии приёмки

1. Никакой пользовательский ввод не приводит к исключению в поиске — ни через экран поиска, ни через
   системный
   `SearchManager` (property-based тест + интеграционный на реальном SQLite).
2. Для украинского текста слово находится при любом варианте: точное, без `ґ/є/ї/і`, с русской
   раскладкой (`ы`, `э`, `ё`), с любым апострофом (включая U+02BC) или без него, с/без ударения,
   любой регистр.
3. Русский и польский поиск не деградируют (golden-набор запросов «до/после»).
4. Размер БД после миграции растёт не более чем на размер FTS-индекса (лирику не дублируем).
5. Миграция 15 → 16 на копии реальной БД проходит без потери данных; `songs_fts` после миграции и
   после последовательности insert/update/delete/REPLACE проходит `integrity-check`; число строк
   индекса = число песен.
6. Сниппет показывает **исходный** текст песни с подсветкой совпадения.
7. Установленная из каталога книга ищется сразу после установки; обновление книги не меняет выбор
   пользователя.

## 3. Дизайн решения для P2

### 3.1. Что нормализуем (один источник истины)

Единая таблица соответствий в `pws-core`, `data/db-room` commonMain (без `java.*`), вида «символ →
итог»:

| Вход                                            | Выход       | Комментарий                                                                       |
|-------------------------------------------------|-------------|-----------------------------------------------------------------------------------|
| `ґ Ґ`                                           | `г Г`       | укр.                                                                              |
| `є Є`                                           | `е Е`       | укр.                                                                              |
| `ї Ї`                                           | `и И`       | укр.; сразу в `и`, не цепочкой через `і`                                          |
| `і І`                                           | `и И`       | укр./бел.                                                                         |
| `ё Ё`                                           | `е Е`       | рус.                                                                              |
| `ы Ы`                                           | `и И`       | рус., для украинцев с русской раскладкой                                          |
| `э Э`                                           | `е Е`       | рус.                                                                              |
| `й Й`                                           | —           | **не** сворачиваем в `и` (D2): «йод»/«иод» редкость, а «мой/мои» — ложные склейки |
| `' ’ ‘ ʼ ` ´` (U+0027 2019 2018 02BC 0060 00B4) | *(удалить)* | апострофы: «п'ять» → «пять»                                                       |
| U+0301 (ударение)                               | *(удалить)* | уже безвредно, делаем явно                                                        |

Таблица задаётся как `Map<Char, String>` («каждый символ → итоговый»), не как цепочка замен —
порядок не важен, и из неё генерируются обе реализации (§3.2). Регистр **не** трогаем ни в Kotlin,
ни в SQL: его сворачивает
`unicode61`; `lower()` SQLite для кириллицы бесполезен (§1.2), поэтому в таблице обе буквы каждой
пары. Опционально (стретч, D5): `ł→l` для польского.

### 3.2. Где нормализуем

**FTS4 с `content=<view>` + собственные триггеры на `songs`; `songs_fts` выходит из-под управления
Room.**

- Вьюха `songs_search_v`: `SELECT id AS rowid, R(name) AS name, R(author) AS author, R(translator) …, R(lyric) AS
  lyric FROM songs`, где `R(x)` — вложенные `replace()`, **сгенерированные из таблицы §3.1**.
  Колонка `rowid` — обязательна (§1.2).
- `songs_fts` — `FTS4(name, author, translator, composer, bibleref, lyric, tokenize=unicode61,
  content=songs_search_v)`.
- 4 триггера на `songs`, имена с префиксом **`pws_fts_sync_`** (не `room_fts_content_sync_` — такие
  Room сносит в
  `onPreMigrate`): `BEFORE UPDATE` / `BEFORE DELETE`: `DELETE FROM songs_fts WHERE docid = old.id`;
  `AFTER INSERT` / `AFTER UPDATE`: `INSERT INTO songs_fts(docid, name, …) SELECT rowid, name, … FROM
  songs_search_v WHERE rowid = new.id`.
- **`SongFtsEntity` удаляется из `@Database(entities)`** целиком. Причины: с `contentEntity` Room
  пересоздаёт свои сырые триггеры после каждой миграции; без `contentEntity` Room-валидация опций
  (`content=`) не сойдётся с БД. Таблицы, не известные Room, он не валидирует и не трогает. Цена:
  `@SkipQueryVerification` на 2 запроса
  `SongDaoBase` и 3 запроса `androidMain/SongDao` (с комментарием «почему»); Flow-запросов по
  `songs_fts` нет,
  `InvalidationTracker` не страдает.
- Весь SQL (create view / fts / triggers / drop / rebuild / integrity-check) — один объект
  `SongSearchSchema` в
  `db-room` commonMain, генерируемый из таблицы §3.1. Его вызывают: `ensureSearchSchema(connection)`
  из
  `RoomDatabase.Callback` (`onCreate` **и** `onOpen`: `IF NOT EXISTS`-идемпотентно; если `songs_fts`
  только что создана — сразу `rebuild`), и `MIGRATION_15_16`.
- Единая точка сборки БД: `fun RoomDatabase.Builder<PwsDatabase>.withPwsSchema(): Builder` в
  `db-room` commonMain (добавляет callback и миграции); все 7 сборщиков из §1.1 переводятся на неё,
  иначе свежая БД в тестах останется без индекса.
- Запрос: тот же нормализатор в Kotlin → `buildFtsPrefixQuery`. Функция **переезжает в `db-room`**
  (рядом со схемой, как её контракт запроса), чтобы `PwsDataProvider` в db-android тоже её
  использовал.

### 3.3. Следствие: сниппет и отображаемые поля

`snippet()` и любые `s.name` из `songs_fts` теперь отдают нормализованный текст. Нельзя показывать
пользователю.

- Все отображаемые поля берём из `songs` (join по `s.docid = songs.id`), не из `songs_fts`. Касается
  и трёх Android-запросов подсказок (`SUGGEST_COLUMN_TEXT_1 = s.name`).
- Сниппет строится в Kotlin по **исходной** лирике: нормализатор отдаёт вместе с текстом карту
  индексов (только удаления → монотонная), токены запроса ищутся как префиксы токенов в
  нормализованной копии, границы переводятся в исходные, окно ±N символов, подсветка
  `<mark>…</mark>` (`HighlightedText` понимает). Делается для ≤ `limit` строк на запрос — дёшево.
  SQL-`snippet()` из запросов убирается. Вынесено в **T-2.5**.

### Фаза 1. Безопасный запрос (P1) — релизится отдельно

- **T-1.1** Красные тесты `buildFtsPrefixQuery`: `(бог`, `а"б`, `бог AND`, `NOT`, `NEAR`, `OR`, `*`,
  `^`, `:`, пустой после очистки, очень длинный ввод, только знаки. Property-based (Kotest
  `Arb.string`, уже в зависимостях): результат либо пустой, либо матчится регуляркой
  `^"[\p{L}\p{N}]+\*"( "[\p{L}\p{N}]+\*")*$`.
- **T-1.2** `buildFtsPrefixQuery`: токен — последовательность `Char.isLetterOrDigit()`
  (KMP-безопасно, без
  `\p{L}` в regex для Native) плюс U+0301; всё остальное — разделитель. Каждый токен → `"токен*"`
  (кавычки снимают вопрос `AND/OR/NOT/NEAR`). Не более 8 токенов. Переезд функции в `db-room`
  (§3.2) — здесь же, чтобы T-1.5 её видел.
- **T-1.3** Интеграционный тест на реальном Room/SQLite (`SongSearchRepositoryImplTest`, jvm): любой
  ввод из T-1.1 → запрос выполняется без исключения; `"свят бог"` по-прежнему находит.
- **T-1.4** Защита на уровне репозитория: `SQLiteException` из `MATCH` → пустая выдача + телеметрия
  `recordError` (без текста запроса, как в `SearchScreenModel`). Проверить, что
  `HomeScreenModel.performSearch`
  тоже не падает на исключении.

## 7. Вне скоупа (заметил по пути, не делаем без отдельного решения)

  константа. Хорошее продолжение: точное совпадение выше нормализованного (после D2 это становится
  заметнее).
- Один и тот же поиск реализован в двух DAO (`SongDaoBase` и `androidMain/SongDao`) — кандидат на
  слияние после T-2.7.
- `getAllActive()` в `BookStatisticDao` помечен `@Deprecated` и дублирует семантику `priority > 0`.
- Нет `app_name` в `values-uk/pl/ru` — норма (берётся из default), не дефект.

## 8. Журнал (заполняется по ходу)

- 2026-10-23, эксперимент SQLite 3.46.1 (Python, `tokenize=unicode61`): `ганок*`/`едини*`/`ижак*`/
  `пять*`/`елка*`/
  `иод*`/`Исус*` → 0 совпадений на «Ґанок Єдиний їжак п'ять … ёлка йод Ісус»; `(бог`, `а"б`, `NOT`,
  `бог AND` →
  `malformed MATCH expression`; `-бог`, `бог:` — без ошибки. Апострофы: U+0027/2019/2018/0060/00B4 —
  разделители, **U+02BC — буква**. View без колонки `rowid` → `docid = 0`, `integrity-check` падает;
  view с `id AS rowid` → всё консистентно после rebuild/insert/update/delete. `"госп*"` — рабочий
  префикс в кавычках, `"госп"*` — нет.
- 2026-10-23, Room 2.8.4 (сгенерированный `PwsDatabase_Impl.kt`):
  `onPreMigrate → dropFtsSyncTriggers`,
  `onPostMigrate` пересоздаёт `room_fts_content_sync_songs_fts_*` с сырым текстом;
  `validateMigration`
  сравнивает `FtsTableInfo` вместе с опцией `content=`.
- T-0.1 (частично, 2026-10-23): **Bundled (jvm) — да**: SQLite 3.50.1, `ENABLE_FTS3_PARENTHESIS`, `ENABLE_FTS4`;
  view-контент + триггеры + rebuild + integrity-check работают (`SongSearchSchemaSqliteTest`, `Migration15To16Test`).
  **SQLCipher — не проверено**: `SearchSchemaAndroidTest` (db-android, Robolectric) готов, сценарий SQLCipher
  отключается с причиной, если нативная библиотека не грузится (на хост-JVM — так и будет) → нужен прогон на
  устройстве. **Native (iOS) — не проверено**: native-тесты db-room отключены, Linux aarch64 не собирает iOS.
- R9 (2026-10-23): Room сам ставит `PRAGMA recursive_triggers = 1` на пишущем соединении
  (`InvalidationTracker.configureConnection`, Room 2.7+, и в driver-, и в SupportSQLite-режиме) → `INSERT OR REPLACE`
  через DAO вызывает `BEFORE DELETE`, индекс консистентен. Без pragma (сырое соединение) — устаревшие токены и
  `integrity-check` падает (красный тест). Попутно: REPLACE песни каскадно удаляет её `song_numbers` (FK ON DELETE
  CASCADE) — существующее поведение, `BookContentWriterImpl` его обходит через `update`.

- T-0.4 (2026-10-23): `androidx.room:room-testing` 2.8.4 для jvm есть; миграция 15→16 тестируется в `db-room` jvmTest (`Migration15To16Test`).
